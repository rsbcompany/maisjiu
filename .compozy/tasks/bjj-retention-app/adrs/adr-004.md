# ADR-004: Backend e dados — Supabase (BaaS), sem backend próprio em Go

## Status

Accepted

## Date

2026-06-30

## Context

O PRD exige modelo relacional/SQL e operação concierge na qual o admin insere semanas, vídeos e tags diretamente via SQL, e consulta as métricas via SQL. Não há código existente (greenfield). O template de techspec deste projeto sugere, por convenção, ao menos uma interface/struct em Go, indicando preferência histórica por backend em Go. O MVP, porém, prioriza velocidade e mínimo custo operacional.

## Decision

Adotar **Supabase** como backend gerenciado: Postgres + Auth + API REST automática (PostgREST) + Storage. **Não** haverá backend próprio em Go; o stack é **TypeScript-only** (Expo no cliente, SQL/políticas no Supabase). Em consequência, a seção de Core Interfaces da techspec será expressa em **TypeScript**, e este ADR registra explicitamente o desvio da convenção Go do template, justificado pela ausência de backend customizado.

## Alternatives Considered

### Alternative 1: API própria em Go + Postgres

- **Description**: Backend customizado em Go seguindo a convenção do projeto.
- **Pros**: Aderente à convenção Go; controle total sobre regras e endpoints.
- **Cons**: Mais esforço de construção, deploy e manutenção; não entrega valor adicional para um teste de validação.
- **Why rejected**: Custo incompatível com o objetivo de validar a hipótese rapidamente.

### Alternative 2: API em Go consumindo Postgres gerenciado

- **Description**: Camada Go fina sobre um Postgres gerenciado.
- **Pros**: Convenção Go preservada; banco gerenciado.
- **Cons**: Mantém o overhead de um serviço próprio sem ganho relevante no MVP.
- **Why rejected**: Supabase já oferece API, auth e RLS prontos.

### Alternative 3: Firebase

- **Description**: BaaS com banco NoSQL.
- **Pros**: Rápido; ecossistema maduro.
- **Cons**: Modelo NoSQL não atende ao requisito relacional/SQL nem ao fluxo de admin via SQL.
- **Why rejected**: Conflita com o requisito relacional explícito do PRD.

## Consequences

### Positive

- Admin via editor SQL nativo do Supabase, atendendo ao modelo concierge.
- Auth, API REST e segurança por RLS prontos, acelerando o MVP.
- Métricas consultáveis diretamente via SQL.

### Negative

- Acoplamento ao fornecedor (Supabase).
- Desvio da convenção Go do projeto (stack TypeScript-only).

### Risks

- Lógica de negócio acoplada a RLS/PostgREST pode exigir refatoração se a Fase 3 (painel admin, multi-academia, cobrança) demandar backend próprio — aceitável como dívida controlada do MVP.

## Implementation Notes

Acesso a dados no cliente via `supabase-js`. Toda a segurança de leitura/escrita é imposta por políticas RLS (ver ADR-005). O esquema relacional e a tabela de eventos de visualização são definidos na techspec.
