# ADR-005: Autenticação e segurança de dados — Supabase Auth + Row Level Security

## Status

Accepted

## Date

2026-06-30

## Context

O PRD define contas pré-criadas, login por usuário/senha e bloqueio de cadastro e recuperação. O documento de ideia (`bjj.md`) propunha uma coluna `senha` em texto na tabela `Users`, o que representa risco de segurança. É necessário proteger os dados dos alunos e o registro de visualizações, garantindo que cada aluno só acesse o que lhe é permitido.

## Decision

Usar **Supabase Auth com e-mail + senha**, com **cadastro (signup) desativado**; as contas são provisionadas pelo admin. As senhas são armazenadas com hash pelo próprio Supabase Auth (nunca em texto). O controle de acesso é feito por **Row Level Security (RLS)** no Postgres:

- Usuários autenticados podem **ler** conteúdo público do app (semanas, vídeos, tags, junção vídeo-tag).
- Usuários autenticados podem **inserir** eventos de visualização apenas vinculados ao próprio `user_id`.
- Usuários autenticados podem **ler** somente os próprios eventos de visualização.
- Operações administrativas (inserção de conteúdo, leitura agregada de métricas) usam a chave de serviço fora do app (editor SQL do Supabase).

## Alternatives Considered

### Alternative 1: Auth própria na tabela Users (como no bjj.md)

- **Description**: Gerenciar usuários e senhas manualmente em tabela própria.
- **Pros**: Controle total do esquema.
- **Cons**: Necessidade de implementar hashing, sessões e proteção contra ataques; alto risco de falhas de segurança.
- **Why rejected**: Reinventar autenticação é desnecessário e arriscado havendo Supabase Auth.

### Alternative 2: Login por "usuário" (sem e-mail)

- **Description**: Identificar o aluno por um nome de usuário em vez de e-mail.
- **Pros**: Pode ser mais familiar para alguns alunos.
- **Cons**: Exige mapear usuário→e-mail interno e desviar do fluxo padrão do Supabase Auth.
- **Why rejected**: Adiciona atrito sem benefício relevante no MVP.

## Consequences

### Positive

- Senhas com hash e gestão de sessão/JWT prontas.
- Isolamento de dados por aluno garantido no nível do banco (RLS).
- Sem superfície de cadastro/recuperação exposta.

### Negative

- Login exige e-mail; alunos sem e-mail dependem de um endereço fornecido pela academia.

### Risks

- Política RLS mal configurada pode vazar ou bloquear dados — mitigado por testes das políticas e revisão antes do piloto.

## Implementation Notes

Desativar provedores de signup no painel do Supabase. Criar contas via editor SQL/admin. Um registro de perfil (ex.: tabela `profiles`) guarda o nome do aluno vinculado ao `auth.users.id` para a saudação do dashboard.
